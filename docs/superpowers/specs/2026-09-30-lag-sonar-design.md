# lag-sonar — дизайн

**Дата:** 2026-09-30
**Статус:** согласован в основных решениях, реализация начата

## Задача

Иконка в menu bar macOS, по виду которой сразу понятно, **на каком уровне** сейчас
проблема со связью. Главный сценарий: Claude отвечает медленно, и нужно за полсекунды
понять — это моя сеть, мой VPN или это у Anthropic.

Существующие индикаторы не годятся: системный значок Wi-Fi показывает лишь наличие
линка, а при поднятом VPN-туннеле он всё равно горит «подключено», даже когда наружу
не проходит ни байта.

## Решения, принятые на этапе обсуждения

| Вопрос | Решение |
|---|---|
| Кодирование состояния | Кольцо + ядро: **кольцо = сеть**, **ядро = Claude** |
| Стек | Python 3.10 + PyObjC 12.2 (уже установлены, Xcode не требуется) |
| Проба Claude | Без API-ключа + опрос статус-страницы. Ноль токенов, ноль расходов |
| Объём v1 | Иконка, меню с раскладом по слоям, автозапуск. Без уведомлений и истории |
| Архитектура | Один процесс: пробы в пуле потоков, отрисовка в главном |

## Установленные факты об окружении

Проверено на живой машине 2026-09-30, не по документации:

1. **macOS 26.5.2**, Apple Silicon. Xcode отсутствует, Command Line Tools содержат
   Swift 5.3.1 и macOS SDK 11.0 — нативная сборка на Swift невозможна без установки
   ~1,5 ГБ обновлений. PyObjC 12.2 с `AppKit` и `Foundation` доступен и работает.
   Модули `Quartz` и `SystemConfiguration` **не установлены** — рисуем через `AppKit`
   (`NSBezierPath`, `NSImage`), топологию определяем через `getifaddrs` и системные утилиты.

2. **Весь трафик по умолчанию идёт в VPN.** Маршрут по умолчанию — `utun8`
   (PepperVPN). Физический интерфейс — `en0` (Wi-Fi), адрес `192.168.0.248`.

3. **Привязка сокета к интерфейсу работает.** `setsockopt(IPPROTO_IP, IP_BOUND_IF=25, ifindex)`
   заставляет соединение уйти мимо туннеля: адрес источника `192.168.0.248` против
   туннельного `10.111.222.0`. Это и есть механизм различения «я / VPN».

4. **TCP-проба через VPN лжёт.** `connect()` к `1.1.1.1:443` через туннель завершается
   за 0,4 мс — VPN-клиент подтверждает соединение локально, ничего не доставив.
   TLS-рукопожатие до того же адреса занимает 2491 мс против 55 мс напрямую.
   **Вывод: все пробы связности выполняются до уровня TLS-рукопожатия, не TCP.**

5. **HTTP-код пробы Claude сам по себе диагностичен.** Запрос `GET /v1/models`
   без ключа:
   - через VPN → `401 authentication_error` за 674–867 мс — API жив и доступен;
   - напрямую через `en0` → `403` за ~110 мс — региональная блокировка, до API не доходим.

   То есть по коду ответа различаются «VPN не пропускает» и «API лёг».

6. **Канал нестабилен.** Одна и та же проба в пределах минуты давала 450 мс,
   таймаут 8 с и 5873 мс. **Вывод: без гистерезиса иконка будет мигать.**

## Архитектура

Один процесс. Границы модулей проведены так, чтобы сеть, решение и отрисовка
не знали друг о друге:

```
lag_sonar/
  config.py     — интервалы, таймауты, пороги, хосты. Одно место для настройки.
  netinfo.py    — топология: физический интерфейс (имя, IPv4, ifindex), шлюз,
                  активен ли VPN и через какой интерфейс идёт маршрут по умолчанию.
                  Только факты, никаких решений.
  probes.py     — независимые пробы, каждая с жёстким таймаутом.
                  Probe(name, ok, latency_ms, detail, extra). Не знает про иконку.
  diagnosis.py  — чистая функция: dict[str, Probe] → Verdict.
                  Ноль ввода-вывода. Вся содержательная логика здесь.
  icon.py       — NSImage 18×18 по паре (ring, core). Не знает про сеть.
  menu.py       — NSMenu из Verdict.
  app.py        — NSStatusItem, таймер, пул потоков. Только склейка.
  cli.py        — тот же вердикт текстом в терминал, без GUI.
```

Проверяемость границ: `diagnosis` прогоняется на выдуманных наборах проб и покрывает
всю таблицу состояний без единого сетевого пакета; `icon` рендерится во все комбинации
и проверяется глазами через контрольный лист PNG; `cli` даёт живую диагностику
без запуска менюбара.

### Пробы

| проба | как выполняется | таймаут | на какой вопрос отвечает |
|---|---|---|---|
| `link` | `getifaddrs`: есть ли у физического интерфейса IPv4 | — | Wi-Fi вообще включён? |
| `gateway` | TCP до шлюза (:80/:443/:53) | 1,5 с | роутер жив? |
| `direct` | TLS-рукопожатие, сокет прибит к физическому интерфейсу | 4 с | провайдер жив мимо VPN? |
| `tunnel` | TLS-рукопожатие по маршруту по умолчанию | 4 с | VPN пропускает трафик? |
| `dns` | резолв `api.anthropic.com` системным резолвером | 3 с | имена разрешаются? |
| `claude_api` | `GET https://api.anthropic.com/v1/models` без ключа, TTFB | 8 с | API жив, быстр, доступен? |
| `claude_status` | `status.anthropic.com/api/v2/status.json` | 8 с | у них объявлен инцидент? |

Хосты для `direct` и `tunnel`: `1.1.1.1` (SNI `one.one.one.one`), запасной `8.8.8.8`
(SNI `dns.google`). Проба успешна, если прошёл хотя бы один — иначе ложное срабатывание
при блокировке одного из резолверов у провайдера.

`dns` выполняется в потоке пула с ожиданием по таймауту: `getaddrinfo` не умеет
прерываться, поэтому зависший вызов просто перестаёт ожидаться, а поток помечен
демоническим.

### Поток данных за один цикл

```
таймер (10 с в норме / 5 с при проблеме)
  └─> netinfo: снимок топологии
       └─> пул потоков: пробы стартуют параллельно, каждая со своим таймаутом
            └─> diagnosis(probes, topology) -> Verdict
                 └─> главный поток: icon.render(verdict) + menu.rebuild(verdict)
```

Пробы никогда не выполняются в главном потоке — иначе menu bar подвисает на время
таймаута, и это видно пользователю.

Разная частота: сетевые пробы каждые 10 с, `claude_api` — каждые 30 с (и каждые 10 с,
когда с ним проблема), `claude_status` — раз в 300 с и немедленно при первом переходе
Claude в плохое состояние. Смысл: не долбить чужую инфраструктуру ради данных,
которые меняются медленно.

## Таблица состояний

### Кольцо — состояние сети

| состояние | вид | условие |
|---|---|---|
| `ok` | зелёное сплошное | линк есть, `direct` ок, `tunnel` ок (или VPN выключен), `dns` ок |
| `dns_down` | янтарное с разрывом | связность есть, но имена не резолвятся |
| `vpn_down` | фиолетовое | `direct` ок, `tunnel` не проходит — виноват туннель |
| `isp_down` | оранжевое | линк есть, но `direct` не проходит — виноват провайдер или роутер |
| `no_link` | серый пунктир | ни у одного физического интерфейса нет IPv4 |
| `unknown` | тусклое серое | измерение ещё не проводилось или не состоялось |

Приоритет при одновременных поломках: `no_link` → `isp_down` → `vpn_down` → `dns_down` → `ok`.
Показывается **самый нижний сломанный слой**, потому что чинить надо его.

Отдельный случай — провалившийся `direct` при живом `tunnel`: провайдер режет
публичный резолвер, но через VPN всё ходит. Это рабочая сеть, и кольцо остаётся
зелёным: кричать не о чем.

`unknown` нужен, чтобы отличать «измерили и всё плохо» от «измерить не удалось».
Без него пустой результат сбора проб выглядел бы как «сети нет» — приложение
врало бы вместо того, чтобы промолчать.

### Ядро — состояние Claude

| состояние | вид | условие |
|---|---|---|
| `ok` | зелёный круг | ответ `401` быстрее порога |
| `slow` | жёлтый треугольник | ответ `401`, но медленнее 1500 мс |
| `blocked` | фиолетовый квадрат | ответ `403` — до API не доходим, нужен рабочий VPN |
| `down` | красный крест | таймаут, обрыв или `5xx` |
| `incident` | красный восклицательный знак | статус-страница подтверждает аварию у Anthropic |
| `unknown` | серый контур | сети нет — судить о Claude нельзя |

Ключевая пара состояний ради которой всё затевалось: **зелёное кольцо и красное ядро**
означает «сеть в порядке, проблема у них».

### Дублирование формой

Цвет продублирован формой: ядро круг / треугольник / квадрат / крест / восклицательный
знак / пустой контур, кольцо сплошное / с разрывом / пунктирное. Иконка 18×18 pt
на произвольном фоне menu bar — полагаться только на оттенок ненадёжно.
Проверяется автотестом: все шесть состояний кольца и все шесть состояний ядра
дают попарно различающиеся изображения.

### Гистерезис

Состояние переключается только после **двух подряд** одинаковых вердиктов. Исключение —
`no_link`: он достоверен мгновенно и применяется без задержки. Без гистерезиса
на текущем канале иконка мигала бы постоянно (см. факт 6).

## Обработка ошибок

- Любое исключение внутри пробы превращается в `Probe(ok=False, detail=...)`,
  цикл продолжается. Одна упавшая проба не роняет приложение.
- Если физический интерфейс не найден, зависящие от него пробы отмечаются
  `skipped` и не влияют на вердикт.
- Пробуждение из сна: подписка на `NSWorkspaceDidWakeNotification` запускает цикл
  немедленно, не дожидаясь таймера.
- Смена топологии (другой Wi-Fi, включение/выключение VPN) обнаруживается сравнением
  снимков `netinfo`; при изменении гистерезис сбрасывается, чтобы состояние
  обновилось сразу.
- Необработанное исключение в цикле логируется в `~/Library/Logs/lag-sonar.log`
  и не прерывает работу таймера.

## Тестирование

- `tests/test_diagnosis.py` — таблица истинности: наборы проб → ожидаемый вердикт.
  Покрывает все строки обеих таблиц состояний и приоритет при одновременных поломках.
  Полностью офлайн.
- `tests/test_icon.py` — рендер всех комбинаций кольца и ядра: изображение создано,
  непустое, нужного размера. Плюс `scripts/render_icons.py` собирает контрольный лист
  PNG для проверки глазами.
- `tests/test_netinfo.py` — разбор вывода системных утилит на зафиксированных образцах
  и выбор физического интерфейса среди мостов и самоназначенных адресов.
- `tests/test_runner.py` — гистерезис, расписание опроса, сброс при смене сети
  и устойчивость к упавшему сбору проб. Время инъецируется, ожиданий нет.
- `lag_sonar/cli.py` — живая проверка на реальной сети без GUI.

Итого 125 тестов, все офлайн, прогон занимает около трети секунды.

## Автозапуск

LaunchAgent `~/Library/LaunchAgents/ru.itlab.lag-sonar.plist` с `RunAtLoad` и `KeepAlive`.
Приложение объявляется `NSApplicationActivationPolicyAccessory` — без значка в Dock
и без окна, только menu bar. Установка отдельным скриптом `scripts/install-agent.sh`,
запускается осознанно, а не при первом старте.

## Что выяснилось при реализации

1. **Модули `Quartz` и `SystemConfiguration` в системе отсутствуют.** Масштабирование
   при отрисовке делается через `NSAffineTransform`, а не `CGContext`; список
   интерфейсов читается напрямую через `getifaddrs` (ctypes), а не через
   SystemConfiguration.

2. **Мост виртуальных машин притворяется сетевой картой.** `bridge100` имеет
   маршрутизируемый адрес `192.168.64.1` и при переборе интерфейсов может быть
   принят за физический. Выбор интерфейса упорядочен: интерфейс маршрута
   по умолчанию → `en*` → прочие, и отдельно вниз отодвинуты самоназначенные
   адреса `169.254.x`.

3. **Замер на живом канале подтвердил ценность затеи.** Первый же запуск показал:
   интернет напрямую 45 мс, через VPN 3,3 с, Claude API 3,6 с, у Anthropic
   всё в порядке. То есть тормозил не Claude, а туннель — ровно то различение,
   ради которого приложение и делалось.

4. **PyObjC требует явной пометки питоновских методов.** Методы класса-наследника
   `NSObject`, не предназначенные быть селекторами, помечаются
   `@objc.python_method`, иначе PyObjC отказывается создавать класс.

5. **Несвежий замер нужно помечать.** Claude опрашивается раз в 30 с, и в меню
   его задержка висела неизменной несколько циклов, выглядя как только что
   измеренная. Кэшированная проба теперь несёт свой возраст, и старше пяти
   секунд он показывается прямо в строке: `4.8 с · HTTP 401 · 9 с назад`.

6. **Проверка на живой сети поймала настоящее событие.** Во время прогона VPN
   на два цикла перестал пропускать трафик: кольцо стало фиолетовым
   с пояснением «Интернет есть, но PepperVPN не пропускает трафик», затем
   вернулось в зелёное. Различение слоёв работает на реальной поломке,
   а не только на выдуманных наборах проб.

## Что сознательно не делается в v1

- Уведомлений нет: на флапающем канале они превратятся в спам.
- Истории и графиков нет: ценность неочевидна, пока не поживём с иконкой.
- Запросов к Messages API с ключом нет: пробы без ключа уже дают и факт доступности,
  и задержку, и признак блокировки.
- Разделения на демон и UI нет: второй потребитель состояния пока не существует.
